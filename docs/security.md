# Accounts and security

The details behind the summary in the [README](../README.md#accounts-and-security).

- **Accounts are optional.** Guests can buy; a registered customer sees their order history and gets checkout filled in. Forced registration is a known cause of abandoned carts.
- **Passwords** follow OWASP ASVS (section V2.1) and NIST SP 800-63B: at least 12 characters and at most 128 (`app.security.password.*`; below 8 the application does not start), any characters including spaces and Unicode (normalized with NFKC), no composition rules, no forced rotation; passwords from a list of 1,257 common ones (the 12-plus-character entries of NCSC's top 100,000, via SecLists, MIT licence) and passwords that contain the email or name are refused.
- **Hashing:** Argon2id with OWASP's recommended parameters (19 MiB memory, 2 iterations, parallelism 1; `app.security.argon2.*`, and a weaker setting than OWASP's lightest stops the start), behind Spring Security's delegating encoder, so the algorithm can change later without a migration. At most four hashes run at once and the rest wait: each one takes 19 MiB, and before that limit 20 simultaneous sign-ins got a 768 MiB container killed for running out of memory.
- **Lockout:** after 5 wrong passwords the account is locked for 15 minutes. The counter lives in the database, so it holds across instances. An unknown email and a wrong password get the same answer. A successful sign-in clears the counter. The lock and its audit entry are written in one transaction, and the log names the account by id, not by email. Known trade-off: anyone who knows a username can keep that account locked, the admin's included; in production, sign-in throttling per account and address, or multi-factor authentication for admins, replaces the hard lock.
- **Sessions** are stored in PostgreSQL (Spring Session), so any instance can serve any request. The cookie is `Secure`, `HttpOnly` and `SameSite=Lax`; only the `local` profile drops `Secure`, so that the demo works over plain HTTP. Forwarded headers from a TLS proxy are honoured. A request that is refused for lack of a login opens no session, so anonymous traffic cannot fill the session table.
- **CSRF:** the token travels in a cookie and comes back in the `X-XSRF-TOKEN` header, the usual setup for a same-origin single-page app.
- **Roles:** `/api/admin/**` needs the admin role, `/api/me/**` any signed-in user, everything else is public. A role matrix test checks every endpoint as a guest, a customer and an admin. A customer's order is shown only to that customer and to admins, and anyone else gets `404`, as if it did not exist. A guest's order is shown to whoever has its link, the usual order-status link of a shop; its id is a random UUID.
- **Admin account:** created on the first start from `ADMIN_USERNAME` and `ADMIN_PASSWORD`. The password must meet the same policy as a customer's and must not contain the username. Without `ADMIN_PASSWORD` on the first start, or with a password that breaks the policy, the application does not start, and the error does not repeat the password. A different `ADMIN_PASSWORD` replaces the password on the next start and ends the admin's open sessions; the creation and every change go to the audit log. The `local` profile accepts the demo password `admin` and warns about it in the log.
- **Configuration and secrets:** `application.yaml` is the production configuration and holds no credentials; the database and admin credentials come from the environment, which the Helm chart fills from Kubernetes secrets. The `local` profile (`application-local.yaml`), which `compose.yaml` and `bootTestRun` turn on, adds the demo database user, the `admin` password, the example catalog, Swagger UI (the shop links it only then), a cookie without `Secure` and trust in private networks as proxies; `ConfigurationProfilesTest` pins both sets of values. The ports in `compose.yaml` listen only on `127.0.0.1`, and Trivy looks for committed secrets in CI.
- **Rate limiting:** token buckets per client address in front of Spring Security: 10 sign-ins per minute, 5 registrations per 10 minutes, 30 orders per minute, 10 imports per minute, 600 other API calls per minute. A refused request gets `429` with `Retry-After`. The rules match the decoded path, so `/%61pi/auth/login` counts as a sign-in. Behind a gateway the client address comes from `X-Forwarded-For`, which the application believes only from a trusted proxy: the production configuration trusts none, the Helm chart requires the gateway's addresses and lets only the gateway's namespace connect (a NetworkPolicy), and the `local` profile trusts private networks, which the browser tests use to give each run its own address ([operations](operations.md#kubernetes)). The buckets are per instance; global limits belong at the gateway ([ADR 6](adr/0006-rate-limiting.md)).
- **Input:** item quantities are 1 to `app.orders.max-quantity` (99) in the quote and the order, counting every line of the same product together; an order total that would not fit its column is refused; control characters are refused in product and account fields and in the search text; the uploaded file name is cleaned before it is logged or stored; an unexpected error returns problem details without internals.
- **Headers:** Content Security Policy, `frame-ancestors 'none'`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Embedder-Policy`, `Cross-Origin-Resource-Policy`, a referrer policy and `nosniff`. Both cookies carry `SameSite=Lax`.
